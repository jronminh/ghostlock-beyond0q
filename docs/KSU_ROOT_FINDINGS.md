### UMH caveat (kernel-spawned task I/O)
The UMH child runs as **uid 0** but its **writes produce no data**: `/data` files are
created but **0 bytes**; socket writes from its daemon never reached the client.
A daemon in a *normal* process works (verified: `[daemon] accepted … uid=2000 … sh -i`),
so it is the UMH-spawned environment that is write-crippled (blocked on *content*
writes; a modprobe-spawned task, see §3, DID print a root prompt to a socket).

## 3. modprobe_path → ROOT (WORKS)
PoC wired into `src/core/fops.c` (env `MP_PATH`): right after the redirect verify it
writes `MP_PATH` into `modprobe_path` (via `data_addr`, verified by read-back) **and
writes 0 to `selinux_enforcing`**. Trigger = exec a file with an unknown binary magic
(`\xff\xff\xff\xff`) → kernel `request_module("binfmt-ffff")` → `call_modprobe()` runs
`modprobe_path` **as root** (`call_usermodehelper`, real path).

**Two hard requirements (both verified on-device):**
1. SELinux must be **permissive first** — while enforcing, the LSM
   `security_kernel_module_request` hook blocks `request_module`, so no helper runs.
2. The trigger file must hold a **non-printable** magic (4x0xFF). `search_binary_handler()`
   only calls `request_module("binfmt-%04x")` when the first 4 bytes are *not* printable —
   a file of `'?'*4` (0x3F, printable) is **silently ignored** and no helper spawns
   (this bug cost a long debug session; `pwn2` must be 0xFF×4).
```
[run] modprobe_path @... <- '/data/local/tmp/mphelper' wr=25 rd=63 rb='...' selinux_off=1
[trigger] /data/local/tmp/pwn2
[check]  15032 root  mphelper -q -- binfmt-ffff
         tcp 0 0 127.0.0.1:2223 LISTEN
[connect] sh: can't find tty fd …  :/ #     <-- root shell prompt (uid 0)
```
Helpers: `src/primitives/mphelper.c` (root daemon; `rootshell.c`) + `pwn2` (the
4×0xFF trigger file, generated by `tools/build14.sh`).
Run: `env … FORCE_REDIRECT=1 SLIDE=0x… MP_PATH=/data/local/tmp/mphelper \
      ./glA17 --stop-after=verify --log=info`  then exec `pwn2`.

## 6. Arbitrary kernel R/W — capabilities exercised (data side)

Primitive after the walk: redirect `/dev/ashmem` fops → configfs arbitrary
read/write via `configfs_read_once` / `configfs_write_once`.
**Gotcha:** in `configfs-only` mode the `pipe_*` helpers are NOT set up — use the
`configfs_*` primitives. Hooks wired in `src/core/fops.c` (env `MP_PATH`).

| # | Capability | Mechanism | Verified |
|---|---|---|---|
| 1 | SELinux off | write 0 → `selinux_enforcing` | ✅ |
| 2 | `modprobe_path` → root helper | write path; trigger bad-magic exec | ✅ root daemon (`call_usermodehelper`) |
| 3 | `core_pattern` → root helper | write `|/data/local/tmp/helper` | written ✅ (crash trigger not tuned) |
| 4 | `kptr_restrict=0` | write 0 → `kptr_restrict` | ⚠️ partial (names visible, addrs hashed) |
| 5 | **cred repoint → any process root** | task-list walk (configfs reads), write `task->real_cred`/`cred` = `init_cred` | ✅ uid 0 |
| 6 | full caps / user_ns | implied by #5 (`init_cred` = root + full caps) | ✅ (via #5) |

Key facts:
- **`call_usermodehelper` (real) DOES write `/data`** — the earlier "kernel-spawned
  task can't write /data" was specific to the *fake work_struct* UMH. So a
  `modprobe_path` root process is a fully functional root (reads/writes `/data`).
- `task->cred` for a live task is a per-task slot; repointing it does not affect
  other tasks sharing the old cred object.
- Use the **canonical** `init_cred` (`canon_addr(INIT_CRED)`) as the new pointer.
- The earlier `cred`-path **wedge came from the W2/pselect write**
  (`do_one_write(task+TASK_CRED_OFF, "W2", 2)`), NOT from touching cred — an
  8-byte **configfs** write to `real_cred`/`cred` is stable.
- `find_task_by_tgid()` in `root.c` uses `pipe_read64` (broken in configfs-only);
  the configfs-based walk in `repoint_task_cred()` finds tasks fine.

## 7. Frontier: code / rodata (still not reachable)
`CONFIG_STRICT_KERNEL_RWX=y` → `.text`/`.rodata` are read-only. Data R/W covers
everything above, but patching code (`module_sig_check`, `sys_call_table`) or
calling `set_memory_rw` needs either (a) editing the kernel page tables via R/W
(+ TLB flush problem) or (b) a kernel call primitive. This is the remaining hard
step for KernelSU-LKM (`CONFIG_MODULE_SIG_FORCE=y`).

## 9. Usable root channel (VERIFIED)
The `modprobe_path` helper runs a **file-driven root command loop** (see
`src/primitives/mphelper.c`): write a command to `/data/local/tmp/rcmd`; the helper
executes `sh -c <cmd>` as root and writes output to `/data/local/tmp/rout`.
```
$ echo id > /data/local/tmp/rcmd; sleep 3; cat /data/local/tmp/rout
uid=0(root) gid=0(root) groups=0(root) context=u:r:kernel:s0
```
Root-only paths work (`ls -l /data/adb` succeeds; the shell gets EACCES).
This is a stable, usable full-root channel without touching code/rodata.

**Operational rules (each cost a debug cycle):**
- **Arm `rcmd` *before* triggering** — the helper daemon reads the command immediately
  on spawn (and polls every 300 ms afterwards).
- **Do NOT delete `rout`/`mp_ran`.** A kernel-spawned process cannot *create* a new file
  in `/data/local/tmp` (fscrypt ENOKEY); it can only truncate/rewrite an existing file.
  Pre-create + `cat` (warm) the channel files from the shell, then trigger.
- **Do NOT exec `mphelper` from the shell to "warm" it** — it forks + `setsid()`s a daemon
  that lingers in the *shell* domain and hijacks `rcmd`. Plain `cat` warms the fscrypt
  metadata just as well.
- A `runcon`/domain change is not available (no `su` binary, `ro.debuggable=0`).

### What "full root" gives (probe_root.sh)
| Item | Result |
|---|---|
| `id` | `uid=0(root) gid=0(root) groups=0(root)` |
| SELinux ctx | `u:r:kernel:s0` (init_cred) ; `getenforce` → Permissive |
| caps | `CapEff=0000003fffffffff` (full) |
| read root-only | `/data/adb`, `/data/misc`, `/data/system`, `/proc/1/exe` ✓ |
| kptr_restrict | 0 (but `/proc/kallsyms` addrs still **hashed** even as root) |
| **create NEW file in /data** | ❌ `Required key not available` (**-ENOKEY**, fscrypt) |
| write EXISTING (warmed) file | ✓ (inode `i_crypt_info` already cached) |

So: full root for privileges/reads/exec, **except creating new `/data` files**
(fscrypt keyring). Fix option: repoint `cred->session_keyring` to a keyring that
holds the fscrypt key (or pre-warm each target inode).

## 10. Samsung protection stack vs "root" (survey)
Kernel knobs / symbols / device state:
- RKP: `CONFIG_UH_RKP`, `RKP_KDP`, `RKP_NS_PROT`, `RKP_DMAP_PROT`, `RKP_CFP`(+JOPP/ROPP) —
  partly **EL3/TEE**. Symbols: `rkp_*`, `security_integrity_current`.
- `CONFIG_SECURITY_DEFEX` (Samsung exec LSM), `CONFIG_FIVE`, `CONFIG_DM_VERITY`(+FEC).
  - **DEFEX, observed:** an `execve()` of a binary under `/data/local/tmp` started by a
    **uid 0** process is blocked and the child is **SIGKILLed**:
    `defex: safeplace violation [task=sh (/system/bin/sh), child=/data/local/tmp/<x>, uid=0]`.
    Non-root (`shell`) execs from `/data/local/tmp` succeed, and the kernel-spawned
    modprobe helper runs — so DEFEX specifically walls off *root userspace exec* from
    non-"safe" paths on this build.
- `CONFIG_MODULE_SIG_FORCE`, `CONFIG_STRICT_KERNEL_RWX`, `CONFIG_KNOX_NCM`, `ro.config.knox=v30`.
- Device: `ro.boot.verifiedbootstate=green`, `vbmeta.device_state=locked`, `flash.locked=1`,
  `warranty_bit=0`, `sys.oem_unlock_allowed=0`, `ro.oem_unlock_supported=1`.

Why uid 0 does NOT break them — the protections are not at ring0:
- **Above the kernel (TEE/EL3)**: RKP/KNOX/Keymaster — the kernel cannot touch them, and
  RKP *watches* the kernel. Observed panic: `RKP CRED PROTECTION VIOLATION
  PC:security_integrity_current+0x448` (reset log `/data/log/power_off_reset_reason.txt`)
  after a cred repoint. => do NOT modify `cred`/task_struct/page tables.
- **Before the kernel (bootloader + AVB/SVB)**: verifies the boot image every boot; root
  cannot influence the next boot.
- **Enforced by ring0 itself**: STRICT_KERNEL_RWX (text RO), MODULE_SIG (unsigned module
  rejected), dm-verity (block RO), fscrypt (needs the key).
- **Unlock flag**: `oem_unlock_supported=1` but `sys.oem_unlock_allowed=0` and it is NOT
  settable even as root; `persistent` block is obfuscated and `param` has no plaintext
  OEM/KG flags => **runtime bootloader unlock infeasible** => no flashed persistence.

Achievable (runtime, data-only, RKP-safe): SELinux off, modprobe_path/core_pattern,
kptr_restrict, and **root via the modprobe helper** (uid 0, full caps) — a transient
userspace root. Not achievable: cred/keyring/page-table edits (RKP), unsigned modules,
code patches, new `/data` files (fscrypt), `/system` writes (verity), persistence.

## 11. RKP internals (from source) + security hardware
RKP is TZ/secure-world firmware, driven by the kernel over **SMC** (`uh_call`, `smc 0`).
`include/linux/rkp.h`:
- Commands: `RKP_WRITE_PGT1/2/3`, `RKP_NEW_PGD`, `RKP_FREE_PGD`, `RKP_EMULT_TTBR0/1`
  (RKP **owns/shadows the kernel page tables**); `RKP_JOPP_INIT`, `RKP_ROPP_INIT/SAVE/RELOAD`
  (control-flow protection); `RKP_MODULE_LOAD`, `RKP_BFP_LOAD`, `RKP_KASLR_MEM`, `RKP_FIMC_VERIFY`.
- `struct kdp_init_struct` hands RKP the exact offsets it guards:
  `uid_cred/euid_cred/gid_cred/egid_cred/type_cred/security_cred/usage_cred`,
  `bp_cred_secptr`, `cred_task/mm_task/pid_task/rp_task/comm_task`, `task_threadinfo`,
  `pgd_mm`, `selinux{ss_initialized}`, `verifiedbootstate`.
- `struct rkp_init` gives RKP `_text/_etext`, `_srodata/_erodata`, `init_mm_pgd`,
  `physmap_addr`, page-table bitmaps (`rkp_pgt_bitmap`, `rkp_s_bitmap_ro/dbl`).
- `CRED_JAR_RO "cred_jar_ro"` — RKP makes the **cred slab read-only**.
- Helpers `rkp_is_pg_protected()`, `rkp_is_pg_dbl_mapped()`, `is_rkp_ro_page()`.
=> RKP deliberately protects **cred, `.text`/`.rodata`, page tables, selinux state,
module/BPF loads, and control flow**. Editing any of those => panic
(`security_integrity_current`). Normal `.data` (modprobe_path/core_pattern/
selinux_enforcing/kptr_restrict) is outside RKP's list -> writable.

Security hardware present (device props):
- **TrustZone/TEE** (RKP + KNOX TEE), **Qualcomm SPU**, **eSE** (`ro.security.ese.cosname=JCOP4.0_0050534A`),
  Boot ROM + e-fuse root of trust.
- `security.securehw.available=false` => **no discrete Knox Vault** (S10e 2019 predates it).
- `security.ASKS.version=6.0`, `security.ADP.version=3.0`, `ro.boot.verifiedbootstate=green`.

## 12. SELinux + persistence hunt (final state)
SELinux (.config): `SECURITY_SELINUX_DEVELOP=y` (runtime `/sys/fs/selinux/load` +
enforce toggle possible), `_DISABLE` off, `_BOOTPARAM` off, `DEFAULT="selinux"`.
- Permissive via `selinux_enforcing=0` is the tool used everywhere (runtime only).
- Loading a custom policy (`/sys/fs/selinux/load`, needs root) is possible, but RKP is
  given `selinux.ss_initialized` in `kdp_init` -> risk; and init reloads the ro policy
  every boot (no persistence).
- init uses the powerful `u:r:su:s0` domain for a few commands (`init.usb.rc`,
  `speg_helper.rc`) — a possible context target (untested).

init rc scan (boot-hook hunt) — no clean hook:
- Every `on property:` action does `copy`/`setprop`/`mkdir`/`start <ro-service>`; no
  `exec`/service runs from a writable path; all `import`s are ro (`/system`,`/vendor`,
  `/prism`).
- `import /prism/etc/init/init.rc` (from `scs.rc`) is dead — no `/prism` partition on
  this XAC unit (can't create the mountpoint: `/` is ro).
- Leads: `MyFilter` creates `/data/DownFilters/{Lib,Lib64,Res,Tex,MyFilter}` (downloaded
  camera filters; some process may `dlopen` `/data/DownFilters/Lib64/*.so` — code-load,
  likely at camera use, not boot); `security.perf_harden=0` relaxes perf; `u:r:su:s0`.

Persistence conclusion:
- **Across reboot: no path.** Boot chain is locked (AVB/SVB `green` + `vbmeta locked` +
  TEE), and unlock is infeasible (`oem_unlock_allowed=0` and not settable even as root;
  `persistent` obfuscated; no plaintext OEM/KG flag in `param`; no rw-rc boot hook;
  setuid `su` impossible: `/data` nosuid, `/` ro).
- **Within a boot: durable** = a resident root daemon (modprobe helper, `init_cred`,
  RKP-safe) reachable via file channel (`rcmd`/`rout`) or TCP+pty; re-arm per boot needs
  a userspace agent (an APK, or a DEX + a trigger) — untested whether the exploit runs
  from an app context (`perf_event_paranoid` / SELinux).

## 13. Bottom line
- Exploit primitives work (walk+redirect ✅, configfs arbitrary R/W ✅).
- Root: via `modprobe_path` (RKP-safe) → uid 0 + full caps (userspace); R/W data side used
  for SELinux off / modprobe_path / core_pattern / kptr.
- Blocked by design: cred/page-table/.text (RKP + `STRICT_KERNEL_RWX` + `set_memory_rw`
  vmalloc-only), unsigned modules (`MODULE_SIG_FORCE`), new `/data` files (fscrypt),
  `/system` (verity), unlock/flash/persistence (TEE + locked bootloader).
- => A **transient userspace root** (per boot). Kernel-level persistence is out of reach
  from ring0 on this locked, verified-boot Samsung device.

## 14. SELinux userspace confinement (what the kernel-domain root can NOT do)
`selinux_enforcing=0` makes `getenforce` report **Permissive**, but the root helper runs
as SELinux `u:r:kernel:s0` (init_cred). Despite `.config` having no `ALWAYS_ENFORCE`, the
**property_service** check still denies every `setprop` from that domain:
```
avc: denied { set } for property=persist.dbg.volte_avail_ovr scontext=u:r:kernel:s0
     tcontext=u:object_r:telephony_config_prop:s0 tclass=property_service permissive=0
init: Unable to set property '...' ...: SELinux permission check failed
```
Also observed: `settings ...` → **killed** (SIGKILL, rc=137); `setprop persist.sys.*` →
denied. So from the kernel domain: no properties, no `settings`, no telephony
(`cmd phone`) — i.e. **no userspace tweaks**.

Consequence: this root is **kernel-level** (kernel R/W, modprobe, `sh -c`, file I/O on
*warmed* inodes) — it is **not** a Magisk-style userspace root. ROM-level tweaks that live
in the framework (VoLTE/carrier props, Settings) are **not directly reachable**.

The one persisted-property path that *is* reachable:
- `/data/property/persistent_properties` is readable **and writable** by the kernel domain
  (an *existing* file → fscrypt `i_crypt_info` cached): `printf "" >> ...` → `rc=0`.
- Its format is Android's **protobuf**: a concatenation of entries
  `0a <len> 0a <namelen> <name> 12 <vallen> <value>` (one per `persist.*` prop). Appending
  entries sets those `persist.*` props **on the next boot** (init loads the file).
- Caveat: the live property service keeps the file authoritative and rewrites it on any
  persist change / shutdown, so an appended entry can be clobbered before a reboot; and
  RKP guards the policy, so a per-domain policy change is out.

Setting a prop *live* would require writing the property-area trie
(`/dev/__properties__/…`, mmap the trie + serial) or a policy change (RKP) — not attempted.

**UPDATE (session 7):** the "policy change" path *is* reachable without tripping RKP.
Marking the `kernel` type permissive in the in-memory `policydb.permissive_map` (not
`__kdp_ro`; `kdp_init()` only protects `ss_initialized`/`selinux_enforcing_boot`/
`selinux_enabled`/`init_sec`) makes `security_compute_av[_user]()` set
`AVD_FLAGS_PERMISSIVE`, so `echo 0 > /sys/fs/selinux/enforce` passes and the kernel
emits the genuine `SETENFORCE(0)` notice → init's cached userspace libselinux AVC
reloads as permissive → `setprop` works live (`avc ... permissive=1`).
Implemented in `src/core/fops.c` + `src/primitives/mpnl.c`. `settings`/`app_process`
remain blocked by DEFEX. See `docs/SELINUX_USERSYNC.md`.
